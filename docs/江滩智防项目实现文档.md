## 3. 产品原则

江滩智防不是单纯的炫酷页面，也不是普通的信息登记小程序，而是一套面向开放式滨水区域的安全治理系统原型。

核心原则：

- 首页看安全：游客一打开就知道当前区域是否开放、风险如何、哪里可以求助。
- 报警先发送：紧急求助页面不堆表单，先发送定位和事件，再补充信息。
- 上报分步填：隐患上报像成熟互联网产品一样分步引导，避免一屏塞满输入框。
- 进度可追踪：上报后要像快递物流一样显示处理状态，体现闭环治理。
- 指挥舱可展示：Web 大屏负责比赛现场的视觉冲击和管理价值表达。
- 系统可降级：AI 不稳定时，仍可通过模拟预警和游客上报完成演示。

## 6. 小程序登录方案

小程序启动后首先进入统一登录页。

页面结构：

```text
标题：江滩智防
副标题：两滩七湾滨水安全治理平台

主按钮：微信一键登录
次入口：工作人员登录
```

游客登录：

- 点击“微信一键登录”。
- 小程序调用 `wx.login()` 获取 `code`。
- 调用后端 `POST /api/auth/wechat-login`。
- 后端通过微信 `code2Session` 获取 `openid`。
- 后端查找或创建游客用户，返回系统 `token`。
- 游客进入游客端首页。

工作人员登录：

- 点击“工作人员登录”。
- 进入工号密码登录页。
- 输入工号和密码。
- 调用 `POST /api/auth/staff-login`。
- 后端校验成功后返回 `token`、`staff_id`、姓名和岗位。
- 进入工作人员端工作台。

手机号策略：

- 第一版游客登录不强制绑定手机号。
- 提交紧急求助或隐患上报时，引导填写联系电话。
- 后续可加入微信手机号授权，但不作为第一阶段强依赖。

## 7. 游客端页面规划

底部导航建议：

```text
首页 | 上报 | 求助 | 进度 | 我的
```

其中“求助”为中间凸起按钮，始终醒目，任何页面都能快速进入报警页。

### 6.1 游客首页

首页目标：让游客快速判断当前区域是否安全，并能迅速进入求助或上报。

建议结构：

```text
顶部：
  江滩智防
  当前定位：3号湾区附近

安全状态卡：
  当前开放：开放中
  风险等级：低 / 中 / 高
  水位：正常
  客流：适中

主入口：
  一键求助
  隐患上报

服务入口：
  湾区状态
  救援点
  失物招领
  安全须知

底部：
  今日安全提示
```

设计建议：

- 不要堆太多功能入口。
- 第一屏优先展示安全状态和求助入口。
- 风格参考大厂生活服务类小程序，清爽、可信、操作路径短。

### 6.2 紧急求助页

该页面参考用户草图：中间一个超大圆形报警按钮，页面极简。

页面结构：

```text
顶部：
  紧急求助
  已定位：3号湾区附近

中间：
  超大圆形按钮
  文案：按住求助
  副文案：长按2秒发送当前位置

底部：
  非紧急情况？前往隐患上报
```

状态设计：

| 状态 | 页面表现 |
|---|---|
| 默认 | 蓝绿色安全光环，显示“按住求助” |
| 长按中 | 橙色进度环，显示“正在确认，请继续按住” |
| 已发送 | 绿色成功态，显示“求助已发送” |
| 失败 | 红色提示，显示“发送失败，请重试” |

交互流程：

```text
进入紧急求助页
  ↓
长按中间圆形按钮 2 秒
  ↓
立即创建高风险求助事件
  ↓
Web 指挥舱出现红色预警
  ↓
工作人员端收到待处理任务
  ↓
游客进入补充信息页
```

重要原则：

- 报警页不做复杂表单。
- 先发送定位和事件，再补充详细信息。
- 长按用于减少误触，建议时长 2 秒。

### 6.3 求助补充信息页

报警成功后进入补充信息页。

字段：

```text
求助类型：
  人员落水风险
  儿童走失
  身体不适
  纠纷求助
  违规下水
  其他

联系电话
现场描述
上传图片（最多3张）
提交补充信息
```

业务逻辑：

- 即使游客不补充信息，求助事件也已经创建。
- 补充信息提交后，更新已有 `risk_event`。
- 联系电话建议必填，但第一版可以允许跳过，避免演示阻断。

### 6.4 安全上报页

上报页处理非即时生命危险的安全隐患。

分类：

```text
违规下水
儿童无人看护
救生设施损坏
夜间滞留
人员聚集
噪音纠纷
环境卫生
其他
```

建议采用分步式表单：

```text
1. 选择问题类型
2. 选择位置
3. 上传照片
4. 补充描述
5. 选择是否匿名
6. 提交
```

大厂化优化：

- 不要一屏堆满输入框。
- 每一步只问一个核心问题。
- 提交后明确告诉用户“可在进度页查看处理状态”。

### 6.5 进度页

进度页用于证明“上报有回音、处置有闭环”。

筛选：

```text
全部 | 求助 | 隐患 | 失物
```

记录卡片：

```text
事件类型
湾区位置
当前状态
提交时间
查看详情
```

状态：

```text
已提交
已受理
已派单
工作人员已到达
已完成
已归档
```

详情页采用时间轴，类似快递物流：

```text
19:31 已提交
19:32 已派单
19:34 工作人员已到达
19:39 已完成处置
```

### 6.6 我的页面

第一版保持轻量。

内容：

```text
微信头像 / 昵称
联系电话
我的求助
我的上报
失物招领
安全须知
隐私说明
关于江滩智防
退出登录
```

必须加入“隐私说明”，因为系统涉及定位、图片、联系方式和求助记录。

## 16. V0.1 已确认实现范围

| 决策项 | 确认结果 |

### 19.1 自动派单规则 V0.1

工作人员任务派发采用“最近在线工作人员优先”的规则。V0.1 规则如下：

```text
1. 系统创建风险事件。
2. 查询当前 online 状态的工作人员。
3. 优先选择同湾区工作人员。
4. 若同湾区无人在线，则按模拟距离选择最近人员。
5. 生成工单并绑定 assigned_staff_id。
6. Web 指挥舱和工作人员端同步显示该任务。
```

V0.1 不做复杂路径规划和真实导航距离计算，距离可先使用湾区权重或预设坐标计算。后续接入地图 SDK 后，再升级为真实距离和路线导航。

### 19.2 求助状态页

报警成功后不直接进入表单，而是进入求助状态页。页面重点是让游客安心，知道系统已经收到求助。

页面内容：

```text
求助已发送
工作人员正在赶往现场
当前状态：已派单 / 工作人员已接单 / 工作人员已到达 / 已完成
预计响应：约 2 分钟
按钮：补充现场信息
按钮：查看处理进度
```

如果游客愿意补充信息，再进入求助补充信息页。即使游客不补充，事件和工单也已经创建。

## 20. 产品风格与专业术语体系

本节为 2026-07-30 讨论确认内容，作为后续 UI 设计、页面文案和业务命名的依据。

### 20.1 三端风格定位

项目整体采用“三端差异化风格”，避免所有端都做成同一种视觉。

| 端 | 风格定位 | 设计目标 |
|---|---|---|
| 游客端小程序 | 亲民、清爽、可信的公共安全服务入口 | 让普通游客愿意用、看得懂、能快速求助 |
| 工作人员端小程序 | 类巡防通/警务通的移动执勤工具 | 让工作人员快速接收任务、判断优先级、完成处置留痕 |
| Web 指挥舱 | 专业应急指挥舱 | 让管理者看到实时态势、调度过程、数据研判和治理价值 |

### 20.2 不同端的视觉边界

游客端不能过度警务化。游客端应避免大量使用“警情、执法、布控、研判”等强执法词汇，避免给普通游客造成压迫感。游客端文案应偏服务化，例如“一键求助”“安全上报”“处理进度”“工作人员正在赶往现场”。

工作人员端可以参考巡防通、警务通、移动执勤工具的设计方式。界面应更硬朗、更高效，突出任务列表、风险等级、处置时限、位置、来源、状态流转和处置反馈。

Web 指挥舱可以采用应急指挥中心风格。用语可以更专业，例如“实时态势”“险情分布”“巡防力量”“任务调度”“处置闭环”“风险研判”“重点湾区”。

### 20.3 术语统一规则

为避免项目过度公安化，同时保持专业性，V0.1 统一使用“险情”和“任务”作为核心业务词。

| 不推荐使用 | 推荐使用 | 使用场景 |
|---|---|---|
| 警情 | 险情 | 面向风险事件、游客求助、AI预警 |
| 出警 | 处置 / 到达现场 | 工作人员状态流转 |
| 派警 | 派发任务 / 自动派单 | 系统派发处理任务 |
| 民警 | 工作人员 / 巡防人员 / 值守人员 | V0.1 不强调公安身份 |
| 执法记录 | 处置记录 / 处置台账 | 任务完成后的历史记录 |
| 布控 | 风险监测 / AI预警 | Web 指挥舱和AI页面 |
| 案件 | 事件 / 险情事件 | 数据库与业务对象 |

核心业务对象命名：

```text
险情事件：表示游客求助、隐患上报、AI预警等风险本体。
```

### 23.9 当前风险与处理原则

npm audit 目前会提示部分中高危依赖，主要来自 Taro/NutUI 生态链的间接依赖。V0.1 阶段暂不执行 `npm audit fix --force`，原因是强制升级可能破坏 Taro 构建链，影响小程序稳定性。

处理原则：

1. 比赛原型阶段优先确保可运行、可演示、构建稳定。
2. 上线前再做依赖安全审查和版本替换。
3. 后端接口不直接暴露敏感操作，演示数据与真实数据隔离。
4. 管理员默认账号仅用于本地演示，后续必须改为可配置密钥和初始化流程。

### 23.11 依赖安全审计补充说明

针对 npm audit 中出现的中高危/严重项，当前判断如下：

1. 短期不会直接导致项目无法构建。项目已提交 `package-lock.json`，后续在同一环境或 CI 中应优先使用 `npm ci`，保证依赖版本按锁文件还原，避免未来安装时自动漂移。
2. audit 报告剩余问题主要集中在微信小程序 Taro 构建链及其间接依赖，例如 `@tarojs/cli`、`@tarojs/components`、`webpack-dev-server`、`swiper`、`postcss`、`decompress`、`adm-zip` 等。大量问题属于开发/构建工具链风险，不等同于后端 API 或业务数据库直接暴露漏洞。
3. 仍需重视生产安全。尤其是 `swiper` 这类可能进入前端运行包的依赖，即使当前页面未使用轮播组件，上线前也应确认最终构建产物是否包含相关代码。
4. 不建议执行 `npm audit fix --force`。当前 npm 给出的 force 方案会把部分 Taro 包降到旧大版本，例如 3.x，属于破坏性变更，可能导致小程序构建链不稳定。
5. 已完成第一轮低风险治理：移除当前未使用的 `react-router-dom` 和 `@nutui/nutui-react-taro`，减少 Web 端和小程序端的无效依赖面。

后续处理策略：

- 比赛 V0.1：锁定依赖、保证构建稳定、避免引入未使用 UI 库。
- 开发阶段：每次新增依赖前先确认是否真正需要，优先使用 Taro 官方组件和自写 SCSS。
- 答辩演示：不把开发服务器直接暴露到公网；Web 指挥舱只在本机或局域网演示。
- 上线前：重新选择 Taro 稳定版本或评估原生微信小程序方案，做一次专门的依赖安全整改。
- CI 阶段：构建命令使用 `npm ci` + `npm run dashboard:build` + `npm run miniprogram:build`，audit 先作为报告项，不作为阻断项；正式上线前再提高为阻断项。
